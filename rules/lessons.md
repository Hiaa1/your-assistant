# 经验与规则（人可读、可手改、进 Git）

这个文件里的条目会被注入到所有 LLM 提示词里，并在 Web 上展示"本次命中了哪几条"。
每条尽量写成"当……时，不要……／应该……"，方便以后被检索和复用。

## 格式

- 一条一行，`- ` 开头；可以加 `[tag]` 便于筛选。
- 写清"错误做法 → 正确做法"，最好带一个反例。

## 条目

- [时间] 不要把"报名截止时间"当成"活动开始时间"：邮件里可能同时出现两个时间，涉及"何时到场"时必须分别标注来源与行号，拿不准就列为待确认。
- [邮件] 判断重要性时，来自导师、教务、课程助教、以及带明确 deadline 的邮件优先；群发讲座/社团广告默认降级为 bulk。
- [输出] 回答里引用了资料时，必须给出 `path:line`；没有依据就直说"资料里没找到"，不要编。
- [讲解] 所有讲解（博客、文档、回答）都要走 explain 的骨架：先写基线（读者现在具体怎么做），再让它在某一步崩掉（要数字、要后果），然后把它插在崩掉那一步（一句话说它管什么），再解释为什么非是这个形状、换个地方为什么不行，最后给一条能验证的命令。不许一上来就抛定义或结论；不必照搬七段模板，但必须从最底层机制一环套一环往外推。反例：直接写「X 是一种用于 Y 的机制」，读者没有任何落点。
